# 摄像头采集到的图像分屏撕裂？

<div class="post-byline"><time datetime="2026-10-18">2026.10.18</time><span>·</span><span>智能车</span></div>

今天排查并解决了一位同学的摄像头采集图像撕裂问题。

## 问题现象

- 在 PC 端 VS 中观察时，补线显示正常。
- 将程序放到车上由单片机运行后，中线值出现异常跳变：直道上本应稳定在 **94**，却偶尔出现 **255**。
- 进一步观察发现，采集到的灰度图呈现明显的分屏、撕裂现象。

## 原因分析

他们将 `image_main()` 放在 DMA 摄像头采集图像中断中，并将中断频率设置为 **50 Hz（T = 20 ms）**。这种放置方式本身没有明显问题，但一个中断周期内同时包含：

1. DMA 图像采集过程；
2. `image_main()` 图像处理过程；
3. 中断进入、退出以及其他任务的开销。

如果这些过程的总耗时接近或超过 **20 ms**，下一次中断就可能在上一次处理尚未完成时到来，从而打断图像采集。这样一来，同一帧图像可能来自不同的采集时刻，最终表现为灰度图分屏或撕裂。

当前代码中包含动态阈值、递归、复杂状态机等较耗时的算法，因此我怀疑 `image_main()` 的运行时间过长，超出了中断周期，并进一步影响了 DMA 摄像头采集。

## 验证结果

我增加了简单的计时代码，测试 `image_main()` 的实际运行时间：

- 当前图像处理代码：约 **13000 μs**；
- 社团提供的原始底层代码：约 **5900 μs**。

切换回社团提供的原始底层代码后，图像撕裂现象不再出现。这说明图像处理耗时过长，很可能是导致问题的主要原因。

## 结论

**`image_main()` 可以放在摄像头采集的中断中，但单次处理时间不能接近或超过中断周期。** 实际设计时还应为 DMA 采集、中断开销和其他任务预留余量。

因此，在编写图像算法时，除了关注 PC 端的显示效果，也要结合实际单片机平台的运算能力和实时性要求，避免使用过于复杂、耗时过长的算法。

## 代码例程：快速检测

```c
int16 runtime;

// 图像运行处
// =========================== 中断内或者循环内 ===========================
system_start();
image_main();
runtime = system_getval_us();
// =========================== 中断内或者循环内 ===========================

// 菜单显示
oled_show_int(2, 2, runtime, 5);
```
